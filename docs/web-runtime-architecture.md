# XPScript web runtime architecture

(c) xpagedeveloper.com 2026

Status: architecture decision for section 18. Production implementation must conform to this document and the regression/security gates defined in `todo/web-runtime-server-todo.md`.

## Decision summary

XPScript will use one shared web runtime with three transport adapters:

1. ASP.NET Core/Kestrel for standalone HTTP/HTTPS hosting.
2. FastCGI responder transport for nginx and other FastCGI-capable frontends.
3. Classic CGI transport for older servers such as HCL Domino.

The transports must normalize incoming requests into the same internal request model. Routing, authorization attributes, compilation, cache, Request/Response/Server/Session/Application objects and script execution must not be reimplemented per transport.

Initial XPScript web application source is trusted server-side application code. The web runtime is not a sandbox for hostile XPScript source. An untrusted/multi-tenant execution mode requires a separate worker-process isolation design and is not implied by this architecture.

## Execution model decision

The initial production model is in-process compiled assemblies loaded through collectible `AssemblyLoadContext` instances, one immutable compiled unit per cache generation.

Reasons:

- avoids a process launch per request
- supports bounded runtime compilation and atomic cache replacement
- allows an old generation to finish in-flight requests while new requests switch to a newly compiled generation
- allows unloading obsolete assemblies after all strong references are released
- keeps transport adapters independent from compiler execution

External worker-process execution remains the required direction for any future untrusted-source or hard multi-tenant isolation mode. The initial runtime must not claim process-level isolation between XPScript applications.

## Project boundaries

The implementation should be split behind XPScript-owned interfaces so transports and cache/execution details can change without changing the language API.

Suggested projects/components:

- `XPScript.Web.Runtime`: transport-neutral request/response/context, routing, web objects, session/application stores, compilation service and cache interfaces.
- `XPScript.Web.Kestrel`: ASP.NET Core adapter and `xpscript web` host.
- `XPScript.Web.FastCgi`: FastCGI responder adapter.
- `XPScript.Web.Cgi`: one-request classic CGI adapter.
- existing `XPScript.Compiler`: the only compiler pipeline. No web-only parser/compiler fork.

## Common request model

Every transport produces an immutable or request-scoped `XpsWebRequest` containing at minimum:

- method
- normalized path and path info
- raw query string and multi-value query collection
- headers as multi-value data
- content type and bounded content length/body stream
- host, scheme, protocol and remote address
- cookies
- cancellation token

Every request receives an independent `XpsWebContext` containing Request, Response, Server and optional Session plus site-scoped Application state.

Request-local state must flow through explicit context parameters or `AsyncLocal`-backed access that is set and cleared by the host. Request/Response objects must never be stored in process-global mutable statics.

## Script entry point and routing

A web script is compiled as a web unit rather than a normal console executable. The deterministic entry convention is:

- top-level web script code is initialization/route declaration only
- request execution invokes `Sub WebMain()` when present
- route functions may be selected from URL path segments when the route is explicitly exported/allowed

Routing precedence:

1. `/` resolves `<root>/index.xps`.
2. `/folder/` resolves `<root>/folder/index.xps`.
3. `/foo.xps` resolves `<root>/foo.xps`.
4. `/foo` may resolve `<root>/foo.xps` when no real directory conflicts.
5. `/foo/save` may resolve `<root>/foo.xps` plus exported route function `save` when no matching directory/script path has higher precedence.

A route function is never callable merely because a function with that name exists. It must pass the web route/export and authorization policy generated by the web preprocessor.

## Route/security attributes

Web attributes are metadata consumed by the web compiler/preprocessor, not arbitrary .NET reflection attributes supplied by request input.

Initial attribute model:

- `[Anonymous]`: route permits unauthenticated execution.
- `[Authenticated]`: route requires an authenticated session/user principal.
- `[Get]`, `[Post]`, `[Put]`, `[Patch]`, `[Delete]`: allowed HTTP method.
- `[Rule:test]`: authenticated user must contain rule `test`.
- `[Rule:!test]`: authenticated user must not contain rule `test`.

Default policy must be configurable but secure. A route without an explicit HTTP-method declaration must not silently accept every unsafe method in production mode.

The user/session principal exposes a case-insensitive bounded rule set. Authorization is evaluated before the XPScript route body executes.

## Path security

All transports use one path resolver.

The resolver must:

- reject malformed percent encoding and NUL/control characters
- decode exactly once according to the chosen URL canonicalization rules
- normalize separators without treating request text as a filesystem path
- reject `.`/`..` traversal after normalization
- construct paths only from the configured site root plus validated relative segments
- call `Path.GetFullPath` and verify the result remains under the canonical root
- apply platform-aware comparison rules
- reject or explicitly constrain symlink/reparse-point escapes
- never use request-controlled compiler output paths
- never serve `.xps` source as a static file

Static-file serving is outside the initial XPScript runtime. Kestrel deployments may opt into ASP.NET Core static-file middleware through an explicit static root that cannot expose `.xps`, configuration, generated assemblies or compiler artifacts.

## Compilation pipeline

Web compilation reuses `XPScript.Compiler`.

Order:

1. canonical script path is resolved inside site root
2. source and Include graph are read
3. Include expansion completes
4. configured source preprocessors run in deterministic order
5. the normal parser/transpiler/compiler pipeline runs
6. a web-target assembly is emitted to an owned private compilation directory
7. assembly is loaded into a collectible `AssemblyLoadContext`
8. an immutable compiled route/entry descriptor is published into the cache

Diagnostics retain original source file/line mapping. Production HTTP responses never include generated C#, physical paths, stack traces, source text or secrets.

## Compilation cache

Cache identity includes:

- canonical site identity and canonical root script path
- root source plus every Include dependency content hash
- compiler/runtime version
- web target/code-generation options
- ordered preprocessor identities and versions
- managed/native reference configuration and relevant dependency identity

The cache is bounded by entry count and estimated memory. Compilation for one cache key is single-flight so concurrent misses do not cause compile storms.

Replacement is atomic. Existing requests retain their immutable compiled generation. New requests use the replacement. Obsolete collectible load contexts are unloaded only after no active request/cache reference remains.

Failed compilation uses a short bounded negative-cache/backoff entry to prevent repeated compile storms while a source file remains broken. Source change invalidates that failure entry.

## Kestrel transport

Kestrel mode uses ASP.NET Core and must not implement an HTTP parser.

Default development bind is loopback. External binds are explicit. Production configuration must define bounded request body size, connection/request concurrency, header/request-line limits, request-header timeout, keep-alive timeout and supported HTTP versions.

Forwarded headers are disabled unless trusted proxies/networks are explicitly configured. Host filtering is required when exposed outside loopback. Client disconnect cancellation flows into `XpsWebRequest.CancellationToken`.

HTTPS uses normal ASP.NET Core/Kestrel certificate configuration. TLS termination may also occur at an explicitly trusted reverse proxy.

## FastCGI transport

FastCGI is an adapter into the common runtime, not a separate web implementation.

The dependency review performed for this architecture did not identify a modern maintained .NET package that clearly satisfies the required .NET 10 responder/server, cross-platform and bounded-parser requirements. Before implementation, repeat the dependency review. If no suitable package exists, implement only the minimal FastCGI responder role behind `IFastCgiTransport` with:

- strict protocol version/type/request-id validation
- checked fixed-width length decoding
- bounded PARAMS/header/body accumulation
- partial-read state machine
- no allocation directly from an unchecked peer length
- no unsafe pointer arithmetic
- deterministic rejection of malformed/truncated/out-of-order records
- fuzz/adversarial corpus and partial-network-read regression tests

Support TCP first. Unix-domain sockets may be added on Linux/macOS through normal .NET socket APIs. Windows FastCGI deployment must be validated separately.

`SCRIPT_FILENAME` is treated as untrusted metadata. Script selection always goes through the configured root/path resolver.

## CGI transport

Classic CGI processes exactly one request from environment variables and stdin and writes CGI status/headers/body to stdout.

It uses the same normalized request/context/routing/runtime objects as Kestrel and FastCGI. Environment values such as `SCRIPT_FILENAME`, `PATH_INFO`, `QUERY_STRING`, `REMOTE_ADDR` and `HTTP_*` are untrusted input. CGI stdout must contain only the HTTP/CGI response. Compiler diagnostics and logs go to stderr or configured logging.

CGI mode is suitable for compatibility hosting such as HCL Domino but is expected to have higher per-request startup cost than persistent Kestrel/FastCGI hosting.

## Response security

Response header names use HTTP token validation. Header names/values and cookie fields reject CR, LF and control characters. Transport adapters own framing and Content-Length decisions.

`Response.Write` writes data and does not claim HTML safety. HTML/URL encoding helpers are explicit separate APIs.

Redirect targets reject CR/LF. Local-only redirect policy may be configured separately from external redirects.

## Session and Application state

Sessions are opt-in. Session identifiers are generated with a cryptographically secure RNG and stored in an HttpOnly cookie, Secure when HTTPS is active, with explicit SameSite policy. Session id rotation is required after authentication/privilege changes.

Session storage is behind `IXpsSessionStore`. The initial in-memory store is bounded, concurrent and site-isolated. Values use a restricted XPScript-safe value model rather than arbitrary CLR object serialization.

Application state is site-scoped, bounded and thread-safe. It never stores Request/Response/context objects. One site's Application state is never visible to another configured root/site id.

## Authentication principal

The web runtime defines a transport-neutral principal containing:

- authenticated flag
- stable user id/name where supplied by the application authentication provider
- case-insensitive rule set

Authentication itself is pluggable. The runtime must not invent a default password database. Route attributes consume the principal and rules after the configured authentication layer has populated it.

## Error behavior

Production defaults:

- routing miss: 404
- disallowed method: 405 with controlled Allow header
- authentication required: 401 or configured redirect policy
- authorization/rule failure: 403
- request/body/limit violation: 400/413/431 as appropriate
- script compile/runtime failure: 500 with opaque request/error id

Detailed compiler/runtime information is logged server-side. Development diagnostics are explicit opt-in and should still redact generated C#, secrets and unrelated filesystem paths.

## Multi-tenant boundary

Initial multi-site hosting can isolate configuration, root, cache, Session and Application state by site id, but trusted scripts still execute in one host process and therefore are not a hostile-code security boundary.

Any claim of mutually untrusted tenant isolation requires separate OS process/container identities, filesystem/network policy and IPC. Collectible `AssemblyLoadContext` is a lifecycle mechanism, not a security sandbox.

## Security verification matrix

Production implementation requires automated coverage for:

- traversal and percent-encoding variants
- symlink/reparse-point root escape
- malformed Host and forwarded headers
- request/header/body limits and slow/incomplete input
- response splitting/header/cookie injection
- route method/auth/rule enforcement
- session fixation/rotation and cookie flags
- concurrent Session/Application access
- cache key site isolation and Include invalidation
- compile single-flight and failure backoff
- stale assembly unload/lifetime behavior
- CGI environment/stdin normalization
- FastCGI malformed records, integer boundaries, partial reads and fuzz corpus
- error redaction and no source disclosure
- graceful shutdown/cancellation

No section 18 production item should be marked `[x]` until its applicable runtime/security regression is green.
